# v0.1 Release Review: Bugs, Redundancy, Latency, Explainability, Evals

Status: draft · 2026-11-15 · reviewed at `93f3805` (branch `fix/extract-entities-prompt`)

> **Update (same day):** the owner's decisions and the applied changes are in
> [v0.1-changes.md](v0.1-changes.md). Decisions: (1) boot fixes done in `ce32158`; (2) the full
> answer is read from the query store, not from `/ask` (by design); (3) undefined terms always
> get a drafted definition that is saved and reused, and CLAUDE.md now says so; (4) evals run at
> deployment. Latency items L1, L2, L3 and L5 are applied.

How this review was done: every tracked file was read (about 3.7k lines). `ruff` and `mypy`
were run, and two suspected config bugs were reproduced in `myenv`. The unit tests were **not**
run (CLAUDE.md: "No testing and evals before version 1"). Every statement here about the tests
comes from reading them.

---

## 1. Summary

The core pipeline is in good shape for an MVP:
- guard → entities → ES/Qdrant lookups → SQL → validate/execute/debug loop → query store
- the SQL safety layer (sqlglot AST checks, read-only transaction, EXPLAIN cost guard, row cap)
- careful prompt-delimiter hygiene

Four things block a v0.1 release:

1. **A fresh setup does not boot or run.** `.env.example` names the wrong DB variable. The
   OpenRouter key variable is missing, and the `langchain-openrouter` dependency isn't declared.
   The DB URL format can't satisfy both SQLAlchemy and the raw `psycopg` callers (see §2.1).
2. **The API hides the answer.** `/ask` returns "Returned 42 rows." but not the SQL, the rows,
   the definitions used, the value mappings, or the assumptions. Showing "how it read the
   question" is the product's core promise.
3. **Two behaviours break the stated CLAUDE.md conventions:**
   - `define_terms` and `generate_sql` answer with *unconfirmed*, LLM-drafted definitions.
   - Unresolved values go into SQL as `ILIKE '%…%'`.

   Both are disclosed in the answer text, but both contradict "no hallucinated definitions /
   ask instead of guessing". A decision is needed (§7).
4. **There is no eval harness.** The 4 small datasets (33 cases) have no runner and no
   evaluators. There is no SQL-correctness dataset, and the unit tests are stale (§5).

The biggest latency win is structural. Three fast-model LLM calls run **one after another**
before any lookup starts. One of them (`analyze_ambiguity`) produces output that nothing
downstream reads.

### 2.4 Latency

**Current critical path.** Arrows are sequential. `∥` means the two run in parallel.

```
guard(LLM fast) → analyze_ambiguity(LLM fast) → [extract_entities(LLM fast) ∥ fetch_schema(new engine + 3 reflection queries)]
 → [ES ∥ Qdrant(local fastembed + 1 query per term)] → define_terms(LLM strong, if a term is undefined)
 → generate_sql(LLM strong) → validate → execute(EXPLAIN + query) → [debug(LLM strong) → validate → execute] × ≤3
 → respond → save_result(new psycopg conn, CREATE TABLE, executemany ≤1000 rows) → response
```

- Best case: **4 serial LLM calls** (3 fast, 1 strong). Worst case: **8** (3 fast, define, generate, 3 debug).
- The default "fast" and "strong" models are the same `nvidia/nemotron-3-ultra-550b-a55b:free`.
  It is a 550B free-tier model with shared rate limits, so tiering currently has no effect, and
  a 429 retry can add seconds to every step.

| # | Change | Saves | Risk |
|---|--------|-------|------|
| L1 | Start `guard`, `extract_entities`, `analyze_ambiguity` and `fetch_schema` **in parallel from START**. Join, then route on `guard`. A rejected question wastes one small extraction call. | 2 fast-LLM round trips (often 1–4 s) | None for quality. Prompts don't change. |
| L2 | Cache the reflected schema (TTL, keyed by source and table) on a pooled engine (B4) | 1 connect + 3 queries per request | Stale schema for up to the TTL. Invalidate on reindex. |
| L3 | Move `save_result` off the response path: `asyncio.create_task` now, the arq job later (design §10). Use a psycopg pool. | 1 connect + DDL + up to 1000-row insert | Lost log rows if the process crashes. Acceptable for v0.1. |
| L4 | Use a real fast model for `fast_model` (for example a Haiku-class model via OpenRouter) and a paid model for `strong_model` in the deployed config | Large and model-dependent | Eval-gated (§5). |
| L5 | Qdrant: embed all terms in one batch and use `query_batch_points`. Load the fastembed model at startup (check whether local embedding blocks the event loop in `AsyncQdrantClient`). | Cold start (model load) + N−1 round trips | Low |
| L6 | Merge `analyze_ambiguity` into `extract_entities` (R7) | 1 more fast call (tokens) | Quality risk. Only do it if the entities and ambiguity evals don't regress. |
| L7 | Record timing per node: add `latency_ms` and `trace_id` to `query_log` (design §13 lists both). LangSmith already gives per-node spans. | (measurement) | None |

Target after L1–L3 (with L4 later): **2 serial LLM calls on the happy path** (1 fast, 1
strong). The design's p95 < 10 s target becomes realistic.

### 2.5 Explainability

Current state: `/ask` returns `category`, `reason`, a one-line `answer`, `entities`,
`resolved_values`, `glossary_hits` and `terms_to_define`. The SQL, the rows and the reasoning
behind them are only in the admin server. Proposed definitions and assumptions are joined into
the `answer` string.

Proposal: build an `Interpretation` object deterministically (no LLM) in `respond`, from state
the graph already has, and return it from `/ask`.

```python
class Interpretation(BaseModel):
    outcome: Literal["success", "needs_definition", "needs_clarification", "no_sql", "failed", "rejected"]
    sql: str | None                       # the SQL that actually ran (after validate/LIMIT)
    columns: list[str]; rows: list[list[Any]]; row_count: int; truncated: bool  # preview capped
    definitions_used: list[DefinitionUse] # term, text, source: "glossary"(id, score) | "proposed" | "column"
    value_mappings: list[ValueMapping]    # phrase -> table.column = 'stored', status, score, alternatives
    unclear_terms: list[TermToDefine]     # from analyze_ambiguity, with how each was handled
    assumptions: list[str]
    repairs: list[Repair]                 # each debug attempt: error, diagnosis
    grounding_violations: list[str]       # used_terms/used_values not traceable to a source
    question_id: str
```

- **Grounding check (cheap and deterministic):** `used_terms ⊆ glossary_hits ∪ proposed ∪
  schema columns` and `used_values ⊆ resolved values`. Every literal in the final SQL's WHERE
  clause comes from the sqlglot AST and must also be one of those values. Show any violation
  to the user. The same check is the hallucination evaluator (§5).
- Keep `answer` as the short human sentence, built from `Interpretation`, so nothing is lost.
- Save `Interpretation` as jsonb in `query_log`, so the admin view and the evals see the same
  object as the user.

### 5.2 Use three layers, not one

| Layer | What | LLM? | When it runs | Gate |
|-------|------|------|--------------|------|
| **Unit** | validator, executor error sanitising, routers, `decide`, filters, CSV parsing, grounding check | no (faked) | every commit, seconds | must be 100% |
| **Component evals** | one dataset per LLM node, calling the node function directly with a hand-built state | yes | when that node's prompt, schema or model changes, and before a release | per-node thresholds (§5.3) |
| **End-to-end evals** | full graph on a seeded demo DB (retail_sales + glossary CSV + ES values) | yes | before a release, and when any prompt or model changes | execution accuracy + zero safety/grounding violations |

Component evals are cheap and point to the node that broke. End-to-end evals catch problems
between nodes, such as B6, where the ambiguity output never reaches SQL generation.

### 5.3 Metrics and v0.1 thresholds

| Suite | v0.1 size | Evaluator (code unless noted) | v0.1 gate |
|-------|-----------|-------------------------------|-----------|
| `guard` | 12 → 40 (+ injection, multilingual, follow-ups) | exact category | accuracy ≥ 95%, and **0 `unsafe` labelled `data_question`** |
| `entities` | 9 → 40 | per-entity P/R/F1 on (normalised text, kind) | F1 ≥ 0.85 |
| `ambiguity` | 8 → 30 | term P/R/F1 (normalised, substring-tolerant) | F1 ≥ 0.8 (design F5) |
| `definitions` | 4 → 20 | `feasible` accuracy, column recall, **infeasible → no expression** | 100% on infeasible cases (never invent), feasible accuracy ≥ 85% |
| `nl2sql_smoke` (new) | 30–50 on `retail_sales` | **execution accuracy**: run the gold and predicted SQL and compare result sets (order-insensitive unless the question asks for order) | ≥ 70% (dev plan Phase 1 exit) |
| `grounding` (new, part of e2e) | 15 (defined, undefined and coined terms) | `used_terms` ⊆ sources, `used_values` ⊆ resolved values, undefined coined term → `needs_definition` | **0 violations** (design F3) |
| `values` (new) | 20–30 on seeded ES | top-1 (table, column, value) + status | top-1 ≥ 90%. Tune `value_min_score`/`ratio` on this set. |
| operational | every e2e run | p50/p95 latency, tokens, debug-loop rate | p95 < 10 s, retry rate < 25% |

Small datasets give noisy scores. Run each suite **3 times** (LangSmith `num_repetitions`) and
gate on the mean, and check the worst run for safety metrics. When a case fails, read the
trace before you add a case or change a prompt.

### 5.4 How to run evals before a deployment (runbook)

1. **Freeze the configuration under test.** Use the exact `fast_model`/`strong_model` slugs,
   the thresholds and the prompt files that will ship. Tag the experiment with the git SHA,
   both model IDs and a hash of `agent/prompts/*`. *Evaluating on a free model and deploying
   on another model doesn't test the deployment.*
2. **Seed the fixtures.** The demo DB (`retail_sales`), `docs/samples/glossary_sample.csv`
   loaded into Qdrant for org `eval`, and ES values indexed for org `eval`. Script this so it
   can be repeated (`python -m evals.seed`).
3. **Sync the datasets.** `evals/run.py` upserts each `evals/datasets/*.jsonl` into a LangSmith
   dataset of the same name. The jsonl in git is the source of truth (same rule as the
   glossary), and the run is skipped if nothing changed.
4. **Run.** `python -m evals.run --suite all --repetitions 3`. Component targets call the node
   functions directly. The e2e target calls `graph.ainvoke`. Evaluators live in
   `evals/evaluators/<suite>.py` as plain functions `(run, example) -> {key, score}`.
5. **Compare with the baseline.** The baseline is the last tagged release's experiment. Gate:
   every §5.3 threshold is met, no metric drops more than 2 points, and safety and grounding
   violations stay at 0.
6. **Review failures by hand** in the LangSmith comparison view. Turn each real bug into a new
   dataset case, so the dataset grows from failures.
7. **Record the result.** Put the experiment link and the score table in the release PR
   (design §8 requires this for prompt and node changes).
8. **After deployment:** sample live traces into an annotation queue. Reviewed thumbs-down
   cases become dataset rows (design §8 "Online").

When to rerun: any change to `agent/prompts/`, `schemas.py` (structured-output fields are part
of the prompt), the model config, the thresholds, or the graph edges.

Build order for the harness: `evals/run.py` + `guard` + `entities` (no infrastructure needed)
→ `ambiguity` + `definitions` (adapter for `schema_hint`) → seed script + `nl2sql_smoke` +
`grounding` → `values`. Check the current LangSmith `evaluate`/`aevaluate` API with the
`langgraph-docs` skill before writing the code.

## 6. Already good (keep it)

- Two separate safety layers (AST validator + read-only txn/timeout/EXPLAIN). Error messages

- Tenant ids normalised once and applied everywhere. ES index names can't be injected, and
  Qdrant has a single mandatory filter helper.

- Prompt-injection hygiene: delimiters and "treat as data" instructions in every prompt.

  removes stale values.
