# v0.1 Release Changes

Branch `fix/extract-entities-prompt`, on top of `ce32158`. Follows the decisions recorded in
[v0.1-release-review.md](v0.1-release-review.md). No features were removed (feature list:
review §3).

## 1. Latency

| Change | Impact | Sample |
|--------|--------|--------|
| **L1: parallel start.** `guard`, `extract_entities` and `fetch_schema` start together and join in `gather`, which routes to `reject` or `define_terms`. | Two fewer LLM round trips before SQL generation. | With every LLM call faked at 300 ms, the stage before SQL measured **0.3 s**. The old path ran 3 calls one after another, so it needed **0.9 s**. A full answer with one draft and two repairs measured **1.65 s**, against 2.1 s computed for the old path. |
| **L2: schema cache.** One pooled engine (`core/db.py`); reflected tables cached for `NLSQL_SCHEMA_CACHE_TTL_SECONDS` (300). | No new engine (and no connection leak) per request. Catalog queries drop to zero on cache hits. | 3 questions → schema reflected **1 time** (was 3, each on a new pool). |
| **L3: store off the response path.** `save_log` (one INSERT, pooled) stays on the path. `save_rows` (CREATE TABLE + `COPY`) runs in the background. | The 1000-row write no longer delays `/ask`. The log row exists by the time the frontend reads it. | `GET /questions/{id}` → `rows_status: "saving"` (poll again) → `"saved"` with rows. |
| **L5: batched glossary search plus warmup.** All terms go in one `query_batch_points` call. The fastembed model loads at startup. A missing collection now means "no hits" instead of a crash. | One embedding pass and one Qdrant round trip per question. The first question doesn't pay for loading the model. | "AOV of best customers" → 1 Qdrant call (was 2). |

## 2. Consistent definitions (decision 3)

- **What changed:** after a successful answer, a definition drafted by `define_terms` is saved
  to the glossary as `proposed` by the new `remember_definitions` node. Later questions
  retrieve that saved entry instead of drafting a new one. An admin upload of the same name and
  section replaces it, and a draft never overwrites an existing entry.
- **Impact:** the same term gives the same answer on every question until a user changes it.
- **Sample:**
  1. "profit by region": no glossary entry, so the draft `profit = SUM(amount - cost)` is used
     and saved as proposed. The answer says *"Using proposed definitions (edit them in the
     glossary if they're wrong): profit = revenue minus cost."*
  2. "profit last month": the saved entry is retrieved, nothing is drafted, and the formula is
     the same.
  3. An admin uploads `profit,Revenue - COGS - returns,metric,,approved`. It replaces the draft,
     and every later question uses the approved definition. (Checked offline: first save → 1,
     repeat save → 0, upload → `approved`.)
- **Unchanged:** a term the schema can't support (for example "super routes") still gets *"I
  don't have a definition for "super routes", and the tables don't have the columns to draft
  one. How should I calculate…"*

## 3. Explainability (stored in the DB for the frontend)

- **What changed:**
  - `respond` builds an `Interpretation` (no LLM) and saves it in `query_log.interpretation`.
    `GET /questions/{id}` returns it with the SQL and rows.
  - `/ask` also returns `outcome` and the `question_id`.
- **Impact:** the frontend can show exactly how each question was read.
- **Sample** (from the offline run):
  ```json
  {"outcome": "success",
   "sql": "SELECT region, SUM(amount - cost) AS profit FROM retail_sales GROUP BY region LIMIT 1000",
   "definitions": [{"term": "profit", "status": "proposed", "origin": "drafted_now", "used": true}],
   "unclear_terms": ["recently"],
   "assumptions": ["Used proposed definition of profit", "Read 'recently' as last 30 days"],
   "repairs": [{"error": "Unknown column(s): ['amt']…", "diagnosis": "column is named amount, not amt"}],
   "ungrounded_terms": []}
  ```
- **Vague terms reach SQL generation (B6).** "recently" and "high" are passed to
  `generate_sql` as `<unclear_terms>`, and the reading the model picks appears in the
  assumptions. *Before:* the reading was picked silently and never shown.
- **`analyze_ambiguity` removed (merged into `extract_entities`).** Extraction now also returns
  `time_period` and `vague_quantifier` entities. That was the only part of the ambiguity output
  anything used; its business terms and metrics duplicated extraction's.
  - *Impact:* one fewer LLM call per question (tokens and cost), one node, one prompt and two
    schemas less.
  - *Sample:* "which products are selling high recently" → entities `high`
    (vague_quantifier) and `recently` (time_period) → assumption *"Read 'recently' as the last
    30 days"*.
  - *API change:* `/ask` no longer returns `terms_to_define`. Vague terms come back in
    `entities` and in `interpretation.unclear_terms`.
  - *Dataset:* `evals/datasets/ambiguity.jsonl` was removed. Its vague-term cases moved to
    `entities.jsonl`; its `business_context` cases no longer apply.
- **Repairs are explained (B7).** Each `debug_sql` round is stored with its diagnosis, and the
  assumptions are updated to match the SQL that actually ran.
- **A new `no_sql` outcome (B8).** It replaces the misleading message *"failed after 0 fix
  attempts"*.

## 5. Less code duplication

- One LLM factory (`core/llm.py`) instead of 4 copies.
- One prompt loader and escaper (`agent/prompting.py`) instead of 6 loaders and 3 escaping schemes.
- Shared prompt facts in `agent/grounding.py`, so nodes no longer import each other's private helpers.
- One outcome rule (`state.outcome_of`) instead of two that disagreed.
- Deleted `open_router.py` (it made a live LLM call at import) and `server.py`.
- 12 unused dependencies moved to `pip install -e ".[later]"`.
- `mypy src`: 9 errors → 0. `ruff check src`: clean.

## 7. Is "results read from the DB" production-ready?

There is no Celery or RabbitMQ code in the repo yet, so this assesses the design and today's code.

**Ready now:**
- `/ask` returns a `question_id`, and the answer, interpretation and rows are read from Postgres.
- `rows_status` lets a reader poll while rows are being written.
- The question id is created by the API, so a queue worker can take over unchanged:
  `graph.ainvoke({... "question_id": id})`.

**Not ready yet:**
1. **`/ask` still runs the whole graph inside the request.** Until a worker does that, one slow
   LLM call holds an API worker. The fix: `/ask` writes a `queued` row and enqueues the job,
   and the worker runs the graph.
2. **Background writes are in-process.** A crash loses them, and the row stays at `saving`.
   Add a sweeper that marks old `saving` rows as `failed`, or move the writes into the queue
   job.
3. **No auth.** `GET /questions/{id}` relies on an unguessable id plus an `organisation_id`
   match. Take the organisation from the session before going public.
4. **One table per question.** It grows the Postgres catalog without limit, so add a retention
   job.

**Celery + RabbitMQ or arq + Redis:** the graph is fully `async`. Celery tasks are synchronous,
so each one would need its own event loop (`asyncio.run`) and wouldn't share the cached clients
or the loaded embedding model. arq is async-native, and Redis is already in the compose file.
Pick Celery only if you need RabbitMQ's routing or delivery guarantees. Either way, only
`core/background.spawn` and `/ask` change.
